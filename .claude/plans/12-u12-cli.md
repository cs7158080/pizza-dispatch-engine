## 5. Readings — where this plan filled a silence

Recorded here rather than resolved silently (`CLAUDE.md` §2). The boundary is U1 §5's, restated in
U2, U3, U5, U6, U7 and U8: a Phase 3 document may fill a silence Phase 2 left; it may not settle an
ambiguity inside a decided record. The one thing of the second kind is commit A, and it was returned
to the developer rather than taken here.

- **R-a — four modules, and a one-directional graph among them.** 11.9 fixes `main.py` and Phase 2
  names no other file. Three things are each touched in exactly one place, and that is the split:
  `httpx` in `client.py`, `input()` in `menu.py`, ANSI escapes in `render.py`, with `main.py`
  composing as the API's and the worker's roots do.

  ```
  main   → client, menu          the composition root: settings, one client, the loop
  menu   → client, render        the loop, the five actions, the selected id
  client → httpx                 paths, methods, the five status names, error classification
  render → client                blocks, columns, colour; one type, and no behaviour
  ```

  **The rule this graph has to satisfy is that it is acyclic, and the first form of this reading
  overstated it as "`render` imports nothing of ours".** That was written against the wrong risk:
  the cycle available here is `render → menu`, because `menu` imports `render` in order to print.
  `render → client` closes nothing, and it is the edge that lets the module which owns formatting
  name the value it formats — `render.api_error` receives `FieldFault` and decides how a validation
  entry reads. Under the stronger claim the same formatting would have had to happen in `menu`,
  which is the module that owns neither.

  **The five status names live in `client.py`.** 3.6 enumerates what the CLI knows as one list —
  *"the endpoint paths, the request and response shapes, and the **names** of the five status
  values"* — and that list is this module's whole content. *Rejected:* a `statuses.py` holding one
  constant, which adds a file without removing a dependency, since `render` does not import it
  either way.
  **`render.py` receives the chain as an argument** — `chain(statuses, current)` — rather than
  importing the constant. That is what keeps the graph acyclic: `menu` imports `render` in order to
  print, so `render` importing anything of `menu`'s would close a cycle.
- **R-b — a failed call is an exception, and there is one place that catches it.** 9.4 fixes three
  display shapes and leaves the mechanism open. `client.py` classifies, because it is what saw the
  response, and raises one of three types; the loop in `menu.py` catches them and hands **values**
  to `render`:

  ```python
  class CliError(Exception): ...
  class ApiError(CliError):            # status, and 6.3's detail
  class TransportFailure(CliError):    # the base URL that was addressed
  class UnexpectedResponse(CliError):  # status, and the raw body
  ```

  *Why not a returned result the caller must inspect.* All five actions behave identically on
  failure — 9.4 states *"Every error returns to the menu"* with no exception — so a returned failure
  would put the same `if` in five places, which is one decision written five times. The precedent is
  one file away: U7's `errors.py` lets a domain error leave as an exception and answers it in one
  registered handler, *"which is what keeps 5.2's mapping out of the routes"*.
  *Why this does not contradict U8's `deserialize_or_none`.* That seam returned `… | None` so the
  consumer would not have to import `SerializationError` — a layer boundary being protected. There
  is no layer here to protect: 3.6 makes the CLI one adapter and it has no core.
  *Three `except` clauses rather than one over `CliError`*, so that each shape reaches the function
  that draws it and `render` never branches on an exception type.
- **R-c — no response is parsed into a schema; the CLI renders the JSON it was given.** 9.4 decides
  the CLI validates nothing, and a Pydantic response model **is** validation: it would turn a
  contract change into a `ValidationError` and a traceback, which inverts the failure mode 9.4
  states in its own words — *"a shape that changed would make the output ugly rather than wrong"*.
  `CLAUDE.md` §3's typed-boundary rule is not waived here so much as inapplicable: it validates
  external input *"before it reaches the core"*, and 3.6 leaves this process without one.
  *What does get a defined type is everything the CLI builds for itself* — the three errors above
  and `FieldFault` below — because those do cross between our own modules.
  *One mechanical consequence, fixed here so no step chooses:* `Response.json()` returns `Any`, and
  `strict` mode's `warn_return_any` rejects returning it. Every such value passes through an
  **annotated local**, never a `cast` — checked against `mypy` rather than assumed, and the same
  choice U7's R-c made for `app.state` and U8's R-d for a `pika` subscript.

  ```python
  body: dict[str, Any] = response.json()
  return body
  ```
- **R-d — one `httpx.Client` for the process, owned by an `ApiClient` that is a context manager.**
  9.4 fixes the timeout at 15 s as *"one value for every call rather than one per endpoint"*, which
  a single client expresses and module-level functions would have to repeat. `ApiClient` takes the
  base URL alone and builds its own client, as `PikaEventPublisher` takes three values and builds
  its own connection; the timeout is a module constant, since 9.4 derived it and refused it the
  `PIZZA_` prefix. `main()` uses it under `with`, which closes on every exit path including the
  `KeyboardInterrupt` 9.1 turns into a normal quit.
  *Five methods and not six:* no menu action calls `GET /health`, which 11.2 makes the healthcheck's
  target rather than a person's.
  *Checked rather than assumed:* `httpx` joins a `base_url` with a leading-slash path correctly with
  and without a trailing slash, and `ClientSettings` already strips one.
- **R-e — `httpx.RequestError` is the transport catch, and nothing wider.** Read from the installed
  0.28.1 rather than from memory: `ConnectError`, `ConnectTimeout` and `ReadTimeout` all descend
  from it, while `HTTPStatusError` is a **sibling** raised only by `raise_for_status()`, which this
  client never calls. Catching `HTTPError` would therefore swallow a class this plan handles
  deliberately. A success whose body does not parse raises `ValueError`, and becomes
  `UnexpectedResponse`: a `200` carrying something other than JSON is outside the contract, not a
  transport fault.
- **R-f — the `422` is parsed into `FieldFault`, and the leading element is dropped only when it is
  `body`.** 9.4 says *"`loc` without its leading `body` element and `msg`"*, which is a rule that
  behaves differently when the leading element is something else — a path parameter reads `path`,
  and a whole-body failure carries `["body"]` alone, where a blind trim leaves nothing to print. So:
  drop the first element **when it equals `body`**, join what remains with `.`, render integer
  elements through `str`, and when nothing remains keep `body` as the label. `type` is not shown
  (9.4). The parse happens in `client.py`, which is what keeps the untyped dictionary out of
  `render`.
- **R-g — the settings load inside `main()`, and the CLI configures no logging.** The process is
  launched as a module (11.9), so `main()` is the first thing that runs and U2 §8's contract — first
  action, one line on `stderr`, exit non-zero, no traceback — is reached without making the module
  unimportable. That is U8's R-a and `entrypoints/schema/main.py`'s shape, copied rather than
  reinvented. **`configure_logging` is not called and could not be:** `ClientSettings` declares one
  field, `api_base_url`, and 10.1 gives `PIZZA_LOG_LEVEL` to the api and the worker alone. Nothing
  under `cli/` imports `logging`; what this process has to say, it prints.

### Step 3 — The menu loop, the five actions, and the one id it remembers

**File created:** `src/pizza/entrypoints/cli/menu.py`.

`run_menu(api)` — the loop 9.1 fixes: print the menu, read a digit, run the action, print the menu
again. It holds one variable, the selected order's id (9.5), and it is the only module that calls
`input()`.

The five actions are 9.2's, and each is a function of the client and the state:

1. **Place an order** — three prompts, `POST`, and the new id.
2. **Register a driver** — one prompt, `POST`, and the new id.
3. **List orders and select one** — `GET /orders` rendered through `table`, with a selector column
   and four of `OrderSummary`'s five fields, **without the id** (9.5); a selection then fetches the
   order and displays it, which is what makes 1.2's step 9 reachable.
4. **Update the selected order's status** — with nothing selected, one line and back to the menu
   (9.5); otherwise a `GET` for the current status, then the chain, then the five values, then a
   `PATCH` with the value the keystroke picked. **`STATUSES[choice - 1]`, never
   `STATUSES[index(current) + 1]`** — 9.2's line, and the whole of what separates the permitted form
   from the one 3.6 rejects.
5. **Quit.**

The loop's two other behaviours are 9.1's and belong to it rather than to 9.4, because neither
becomes a request: an unusable choice prints one line and loops, and **`EOF` and `KeyboardInterrupt`
exit as `quit` does, status `0`** — without which 9.3's container reads `EOF` at its first prompt
and produces a traceback.

**Definition of Done**

1. The file exists, with five actions, one loop, and one piece of remembered state.
2. The five commands of §4 exit zero.
3. `pytest tests/unit` still collects nineteen. Every action needs a running API and a person typing
   at it; 12.3 owns the first and gives the suite no path to the second.
4. Read from the diff: **nothing from `domain/` or `application/` is imported** (3.6); no status
   value is derived from another status value, anywhere, by any expression (9.2); no field is
   checked before it is sent (9.4); nothing is written to disk and nothing but the id is kept
   (9.5); `input()` appears in this module and no other; every `except` names one of step 1's three
   types, apart from the loop's own exit — `(EOFError, KeyboardInterrupt)`, which this step's body
   requires and which catches nothing a call can raise.

### Step 4 — Assemble the interactive cli

**File created:** `src/pizza/entrypoints/cli/main.py`.

The composition root, and the third entry point in the system. Everything in it is a construction or
a call:

```python
def main() -> None:
    try:
        settings = load_client_settings(os.environ)      # R-g — first action
    except ConfigurationError as error:
        print(error, file=sys.stderr)
        raise SystemExit(1) from error

    with ApiClient(settings.api_base_url) as api:        # R-d — one client, closed on every path
        run_menu(api)


if __name__ == "__main__":
    main()
```

The `if __name__` guard is what 11.9's `python -m pizza.entrypoints.cli.main` needs, as
`entrypoints/schema/main.py` and `entrypoints/worker/main.py` both have it.

**Definition of Done**

1. The file exists, with the content stated and nothing else.
2. The five commands of §4 exit zero.
3. `pytest tests/unit` still collects nineteen.
4. `PIZZA_API_BASE_URL=… python -c "import pizza.entrypoints.cli.main"` succeeds with nothing
   running — construction performs no I/O, which is what makes `docker compose run --rm cli` fail at
   a screen rather than at an import when the API is down.
5. Running the module with **no** `PIZZA_API_BASE_URL` prints one `invalid configuration:` block on
   `stderr` and exits `1`, with no traceback — U2 §8's contract, checked rather than assumed.
6. Running it against a base URL nothing is listening on prints 9.4's transport screen, naming that
   URL, and **returns to the menu** rather than exiting — the only one of 9.4's three shapes
   observable before U9.
7. Read from the diff: this module imports **nothing from `infrastructure/`** — unlike the other
   three roots, it needs none (3.1); it contains no `async def` (2.4); it decides nothing and
   renders nothing.

## 7. Ordering, and where it is free

Two edges are forced and everything else follows from them.

- **1 → 3, 4:** the actions call the five methods and catch the three types; the root constructs
  `ApiClient`.
- **2 → 3 → 4:** the actions print through `render`; the root runs the loop.

Steps 1 and 2 are independent of each other and could be taken in either order — `render` takes the
chain as an argument precisely so that it needs nothing from `client` (R-a). They are numbered as
they are so that the module a reviewer reads first is the one that defines the contract. **No step
depends on a step after it, and no step needs a file a later step creates**, so each of steps 1 to 3
type-checks on its own even though nothing runs until step 4.
